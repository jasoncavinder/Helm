## Narrow Supported Action

The finite `manager.clear_selected_executable_override` action can propose a
repair only for an explicitly enabled `mise` manager whose saved executable is
definitely absent and whose complete, bounded local observation contains exactly
one distinct native alternative. Aliases of that binary are deduplicated.
Scripts, shims, partial observations, unknown/disabled managers, uncertain absence
and multiple distinct alternatives do not produce an actionable plan.

Proposal reads metadata and stored preferences only. It does not run mise,
acknowledge first run, accept terms, enable a manager, edit shell files, install
packages, initialize ordinary detection, or claim that a file is usable.
The plan binds every existing manager preference and the canonical executable's
device/inode/size/mode/modification/change metadata. A changed proposal requires
review again. The fingerprint is local evidence, not an executable signature.

Applying the reviewed action clears only Helm's saved path. An immediate SQLite
transaction compares all reviewed preferences and current policy, rejects active
mise tasks, and records an applied/unverified receipt together with that change.
Other preferences, selections, inventory, tasks, and acknowledgment are preserved.

Verification runs the bound absolute binary with structured `--version` arguments,
working directory `/`, a 10-second limit, private 4-KiB combined output, and explicit
offline/automatic-update-disabled settings. These are documented
[mise settings](https://mise.jdx.dev/configuration/settings.html); this is not a
sandbox or authenticity proof for a malicious substituted local executable.
No shell, installer, network operation or elevation is requested. The global
selected-executable and timeout overrides cannot replace this reviewed request.

Success requires an exit-zero, valid mise-style version, unchanged executable and
absence evidence, and an atomic final check of the expected preference/policy.
This verifies **the saved override was cleared and this bound executable answered
a version check**, not PATH precedence, package health, or whole-manager readiness.
It does not write a fabricated current detection or inventory snapshot.

## Durable Failure and Review Boundaries

- Migration 22 appends the narrow repair-receipt table; existing migration
  identities remain unchanged. It is not a generalized setup scheduler.
- Failure to write the initial receipt rolls back the preference change.
- A failed version check stays applied but verification-failed. Concurrent user
  changes are preserved, never rolled back or overwritten.
- Interruption or final receipt-write failure leaves applied/unverified truth.
  Startup does not retry, resume, restore, or claim the repair completed.
- A finalized receipt cannot be overwritten by a late callback. There is no
  automatic rollback promise; restoring a removed executable is outside scope.
- FFI review/apply require prepared, legally accepted, unacknowledged startup
  with no activated runtime. Apply consumes the exact process-local review token
  once; another review or preparation invalidates it. Failed transport/storage
  replies require receipt readback, not a blind retry.
- Stored paths and receipts remain local. No telemetry, shared fingerprint,
  automatic export, or new copy-to-clipboard behavior is introduced.

The production GUI/CLI must consume this same core action rather than rebuilding
its eligibility or result logic. This slice adds the prepared FFI boundary, not a
new general CLI setup command or production UI activation.
