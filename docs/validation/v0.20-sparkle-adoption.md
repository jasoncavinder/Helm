# v0.20 External Sparkle Per-App Adoption

## Scope

The owner approved explicit per-app "Let Helm manage updates" adoption on
2026-10-02 for apps whose installation history Helm cannot prove. This implements
the shared-core policy/persistence foundation, not a shipping button, command,
native authority adapter or working installer. Open App remains unchanged.

Valid signatures and absent manager markers do not establish standalone
provenance. `UserAdopted` is a distinct authority derived from explicit consent,
never a relabeling of native `unresolved` evidence as `Standalone`. Known manager
claims always win; unreadable/incomplete native collection is not adoptable.
No existing app is adopted automatically, and migration does not infer consent.

## Contract

- `AdoptionRequest` is independently versioned, size-bounded and rejects unknown
  fields. It carries a consent ID, path, bundle ID and installed build only.
  Clients cannot provide feeds, signatures, roots, authority, tokens or commands.
- The authenticated coordinator must collect fresh target and boundary evidence
  before review and confirmation. The existing exact helper/caller/channel,
  native signature, location, permission, framework and self-exclusion checks
  remain mandatory. The policy module itself does not authenticate a process.
- Preparing a review does not write consent. Confirmation consumes the review,
  expires after 120 monotonic seconds and compares the complete observed target,
  boundary and prior database epoch/path revision. Identity drift, revocation,
  another winning review or a different database cannot silently replace consent.
- Migration 24 appends permission/revocation history. Consent IDs remain consumed
  across revocation and task-history deletion. Every consent/revocation write
  requests FULL/fullfsync durability; ordinary cache connections are unchanged.
- Ongoing permission binds canonical path, bundle ID, signing team, Sparkle key,
  feed and framework major. Build, inode and code hash may change with normal
  vendor updates; they remain bound exactly in each adoption/update review.
  Moved apps or changed vendor/update identities require new adoption. A new
  successful native observation is required every time the grant is resolved.
- Adoption does not create an update session or authorize an installation.
  Candidate compatibility, exact update review, confirmation and one-shot
  durable handoff remain separate. The adoption revision is part of that review.
- Session claim, install handoff and successful version verification recheck the
  current identity-bound grant in their own write transactions. A cached token
  is insufficient after revocation or when transferred to a different target.
- Revocation works in safe mode and appends a tombstone even without a prior
  grant, fencing pending adoption dialogs. It does not terminate an installer
  already handed off. A revoked/uncertain active session retains its recovery
  reservation, and cannot be overwritten by re-adopting the same target.
- Reset/downgrade is blocked while any external update holds a target, before
  either ledger can be removed. A permitted reset forgets consent; a new random
  epoch prevents old in-memory reviews/tokens from becoming current when row
  sequences restart. This is not protection against user database tampering or
  restoration of a historical backup, nor an absolute power-loss guarantee.

The review and receipt are output-only. Neither can be deserialized as permission
over IPC. Local records contain private paths, vendor/update configuration and
review fingerprints; future diagnostics must redact them. The helper must never
accept a caller-selected database or turn serialized receipts into native trust.

## Verification

All 50 focused external-update tests pass in the disposable macOS 27.0 arm64 VM
(26A5378j, Rust 1.98.1), including 20 new adoption regressions. The full Rust
workspace passes: 891 core, 240 CLI and 118 FFI unit tests plus integration
suites, with five existing ignored cases. The complete
`scripts/ci/check_sqlite_migration_compatibility.sh` gate passes in that VM.
Host workspace/all-target Clippy, formatting, immutable-manifest and docs-sync
checks pass; no host application or runtime test was used.

Coverage includes strict requests, no-consent fallback, fresh-boundary/target
rejection, identity/configuration binding, normal vendor replacement, review
expiry/drift, independent-handle revocation before claim/handoff/verification,
eight-way concurrent adoption confirmation, consent-ID replay, safe mode,
task-history preservation, injected write failure, reset/downgrade epoch fencing
and migration preservation. Adopted updates still need exact candidate review,
durable handoff, installer completion and fresh installed-version verification.

The first run stopped before testing because the isolated offline cache lacked
current locked dependencies; permitting Cargo downloads into this scope corrected
the harness without changing the lockfile. The next run caught a real migration
edge: downgrade commits per version, so migration 24 could disappear before the
existing migration-23 active-session guard blocked reset. The guard now protects
both versions. Both preservation regressions pass in the final full rerun.
