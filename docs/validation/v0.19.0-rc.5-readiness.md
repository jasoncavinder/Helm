# v0.19.0-rc.5 Readiness Validation

This is the focused acceptance pass for changes merged after `v0.19.0-rc.4`.
It authorizes no tag, release, appcast, CLI metadata, or website mutation.

## Preconditions

- [ ] Test a clean development-signed build from current `dev` using the `Helm-Development` database namespace. An environment variable supplied to the app process is not inherited by its embedded XPC service, so app-level `HELM_DB_PATH` isolation is not a valid GUI QA precondition.
- [ ] Treat development signing as valid only for ordinary UI and contract checks. The release pipeline has no private signed/notarized candidate mode, so launch-daemon registration evidence must come from the installed RC5 artifact after publication.
- [ ] Run a full manager detection before refresh-dependent checks and confirm the expected local managers are present; do not reuse a stale development inventory as acceptance evidence.
- [ ] Keep the installed signed RC4 app separate from the development build.
- [ ] Confirm macOS notification permission is enabled for Helm when testing delivery and actions.
- [ ] Keep the Environment Brief production gate unchanged; Issue `#388` is outside this pass.

## Native Helper Installed-Candidate QA

These checks run after RC5 publication. They gate later executor activation, not
RC5 publication, because unsigned or development-signed builds cannot establish
the release signing, notarization, installation, or Service Management boundary.

- [ ] Install `v0.19.0-rc.5` through Sparkle from the signed `v0.19.0-rc.4` Developer ID app and confirm the resulting `/Applications/Helm.app` passes strict code-signature assessment.
- [ ] In General Settings, confirm System Authorization begins in the truthful current state and never registers automatically.
- [ ] Choose Register Helper and confirm Helm either reaches Registered or presents Approval Required and opens macOS Login Items without reporting a generic registration failure.
- [ ] If approval is required, approve Helm in Login Items, reactivate Helm, and confirm the state refreshes to Registered.
- [ ] Quit and relaunch Helm and confirm the registered state persists.
- [ ] Choose Unregister Helper and confirm the state returns to Not Registered without leaving an active orphan helper service.
- [ ] Register again only if needed for the later executor-activation slice.
- [ ] Confirm privileged operations still use the existing askpass path; registration alone must not activate native execution.
- [ ] Record denial or unavailable-state behavior encountered during this pass. Exercise update-replacement behavior with the next signed candidate rather than claiming it from the first registering build.
