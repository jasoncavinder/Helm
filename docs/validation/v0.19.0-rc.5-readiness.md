# v0.19.0-rc.5 Readiness Validation

This is the focused acceptance pass for changes merged after `v0.19.0-rc.4`.
It authorizes no tag, release, appcast, CLI metadata, or website mutation.

## Preconditions

- [ ] Test a clean signed build from current `dev` using the `Helm-Development` database namespace. An environment variable supplied to the app process is not inherited by its embedded XPC service, so app-level `HELM_DB_PATH` isolation is not a valid GUI QA precondition.
- [ ] Run a full manager detection before refresh-dependent checks and confirm the expected local managers are present; do not reuse a stale development inventory as acceptance evidence.
- [ ] Keep the installed signed RC4 app separate from the development build.
- [ ] Confirm macOS notification permission is enabled for Helm when testing delivery and actions.
- [ ] Keep the Environment Brief production gate unchanged; Issue `#388` is outside this pass.

## Automated Gates

- [ ] Full repository quality gate passes.
- [ ] arm64 macOS UI tests pass while retaining the macOS 13 deployment target.
- [ ] Locale integrity, locale parity, overflow, and hardcoded-string checks pass.
- [ ] Documentation sync passes.
- [ ] Release rehearsal and preflight remain deferred until the final RC5 candidate is integrated into a clean `main` revision.

## Privileged Execution Contract

- [ ] Automated Rust coverage confirms an elevated request without a typed privileged operation fails before process spawn.
- [ ] Automated adapter coverage confirms MAS, Software Update, Xcode Command Line Tools, Rosetta, and MacPorts mutations emit their expected stable privileged-operation identifiers.
- [ ] Automated Rust coverage confirms Mac App Store mutations stay on the existing askpass path even when a trusted privileged executor is configured.
- [ ] Until the native helper completion gates pass, confirm RC5 documentation and UI do not claim that Helm uses a Service Management launch daemon or system-managed helper approval.
- [ ] Confirm ordinary non-elevated Homebrew work remains unprivileged and unchanged.

## Status Item Routing

- [ ] With Dashboard closed, primary click opens the popover.
- [ ] With Dashboard closed, secondary click opens the same popover.
- [ ] With Dashboard open, primary click focuses Dashboard without replacing it with the popover.
- [ ] With Dashboard open, secondary click opens the popover alongside Dashboard.
- [ ] The popover still exposes an unambiguous Quit action.

## Sparkle Plan Actions

- [ ] A discovered third-party Sparkle update appears in Plan as an interactive step and is not counted as automatic Upgrade All work.
- [ ] The Plan row and inspector both expose the vendor update action.
- [ ] The Plan row and inspector both expose Open App as a fallback.
- [ ] Automatic Plan work leaves unresolved third-party Sparkle steps visible and provides the existing in-app/background handoff.

## npm Incremental Search

- [ ] An empty or one-character trimmed npm query invokes no npm remote search, returns no npm remote results, and surfaces no npm error.
- [ ] A two-character npm query follows the normal remote-search path.
- [ ] Other manager search behavior remains unchanged.

## Actionable Notifications

- [ ] Notifications are enabled by default for a profile with no stored preference and can be disabled in Updates settings.
- [ ] A newly observed update snapshot notifies only while both Helm interfaces are hidden.
- [ ] Repeating the same update snapshot does not deliver another notification.
- [ ] Review Plan opens Dashboard directly to Plan.
- [ ] Upgrade All appears only when currently eligible automatic work exists, opens Helm's existing confirmation sheet, and starts no work directly from the notification.
- [ ] Disabling notifications removes pending/delivered Helm alerts and prevents subsequent delivery.
- [ ] Completing routine tasks produces no “all tasks complete” notification.
- [ ] Timeout decisions and remaining interactive Plan-step notifications remain available when enabled.
- [ ] Changing Helm's in-app language refreshes notification action labels for later notifications.

## Settings Routing

- [ ] Command-Comma opens the native Settings scene from a cold launch.
- [ ] Popover and Dashboard Settings routes open that same scene.
- [ ] Repeated routes focus one Settings window rather than creating duplicates.
- [ ] Xcode logs do not contain “Please use SettingsLink for opening the Settings scene.”

## Outcome

- [ ] Every release-blocking finding is fixed and revalidated, or RC5 preparation remains blocked.
- [ ] Non-blocking observations are documented separately rather than widening RC5 scope.
- [ ] After this pass, prepare the RC5 version/release PR and repeat mandatory release gates before requesting tag/publication approval.
