## Reproduction Shape

Run only in an approved disposable scope with isolated HOME, TMPDIR,
CARGO_HOME, install roots and target directories. Use an exact toolchain and
retain stdout/stderr, exit status and native receipts. Commands below omit those
scope variables for readability and are not instructions to run on production:

```text
cargo install --force --version 1.18.1 --root <unlocked-install> --target-dir <unlocked-target> --jobs 4 slint-viewer
cargo install --force --version 1.18.1 --root <locked-install> --target-dir <locked-target> --jobs 4 --locked slint-viewer
```

## Implementation Requirements, Not Delivered Behavior

The [Cargo install documentation](https://doc.rust-lang.org/cargo/commands/cargo-install.html#dealing-with-the-lockfile)
describes a published-lockfile preference rather than a universal safety proof:
ordinary installation resolves dependencies anew; requesting the published set
can also forego later dependency fixes. Keep the distinction explicit in Helm.

The next implementation should meet all of these requirements before #564 closes:

1. Resolve and bind the reviewed package, exact candidate version, source and
   install scope before execution. Current Cargo upgrade requests are unversioned;
   a candidate version in a preview is not an execution pin.
2. Read the native installation receipt before upgrading. Preserve supported
   feature/bin/profile/target choices; fail closed for unsupported, ambiguous,
   Git/path/private-registry receipts rather than silently replacing them with a
   default crates.io build. Do not infer provenance from a display name alone.
3. Define the missing/stale-lockfile boundary explicitly. Recommended default:
   block automatic locked execution when the reviewed dependency set cannot be
   established, with truthful guidance for manual handling. `--locked` alone
   cannot implement this promise; validating a registry lock graph remains work.
4. Never silently retry unlocked, switch to cargo-binstall, alter global Cargo
   configuration, or pin rustix in Helm's own workspace. Those are different
   actions, not equivalent retries of reviewed work.
5. Verify the observed installed version/source/receipt after success. Current
   install results can use the requested version without checking actual state;
   current upgrade results can use the old preview candidate. Neither is proof
   that the reviewed artifact was installed. Verification must not depend solely
   on a fresh remote search reporting no remaining update.
6. Cover command construction, absent/stale/malformed receipt and lock data,
   source/feature drift, failure preservation, cancellation, actual-version
   reconciliation, and bounded build-timeout behavior through Helm CLI in the VM.
   Follow with signed GUI diagnostic/Plan parity QA. Preserve the #569 diagnostic
   and persistence-race regressions while integrating these changes.

This record closes the reproduction uncertainty, not the product issue. No
Cargo install/upgrade default, release gate or owner approval has changed.
