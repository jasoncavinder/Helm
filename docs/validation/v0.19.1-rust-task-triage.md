### Cargo Toolchain

The exact task 84 error is:

```text
the 'cargo' binary, normally provided by the 'cargo' component, is not applicable to the 'stable-aarch64-apple-darwin' toolchain
```

Task 65 repeats the signature. The failure precedes inventory parsing. Logs do
not establish why the selected component was unavailable or prove a concurrent
rustup update caused it. Later Cargo tasks reached compilation, and read-only
inspection now finds a Cargo binary and component entry. Do not infer an ongoing
broken toolchain or automatically reinstall/change the user's default.

PR #558's operation-specific Command Line Tools checks address a different
prerequisite. They neither establish rustup component health nor remediate this
historical condition. #562 covers actionable, localized prerequisite diagnostics,
cache preservation, explicit repair consent and isolated recovery coverage.

### rustup DNS

The recorded failure contains `dns error: failed to lookup address information`.
This proves name resolution failed for the request, not that every network path
was offline. A resolver/VPN/endpoint incident or a connectivity transition cannot
be distinguished retrospectively.

`should_retry_transient_refresh_error` already recognizes this signature in both
baselines. Existing offline work is therefore not a newly delivered fix for task
124. #563 adds diagnostic/recovery coverage without unbounded retries, mutation
retries, cache clearing, fake success or global-offline inference from one host.

### Cargo Dependency Resolution

The downloaded slint-viewer 1.18.1 Cargo.lock contains rustix 1.1.4 as well as a
separate 0.38.44 entry. Both failed installs instead resolved rustix 1.1.5; its
libc socket code references `crate::timespec`, but that module was configured out
for the compiled feature combination. This is a package-dependency compilation
failure, not a failure compiling Helm itself or proof of absent developer tools.

Cargo normally re-resolves dependencies during install; `--locked` uses the
published dependency set, with the tradeoff of foregoing newer dependency fixes.
See the [Cargo install lockfile documentation](https://doc.rust-lang.org/cargo/commands/cargo-install.html#dealing-with-the-lockfile).
A locked slint-viewer build was **not** tested at this initial investigation
checkpoint. A subsequent [isolated VM comparison](v0.20-cargo-dependency-reproduction.md)
now reproduces the unlocked failure and verifies the native locked build;
Helm's general Cargo policy remains unchanged. The cargo-binstall special case does
not change general Cargo upgrades. #564 requires VM reproduction, a reviewed
lockfile policy, preservation/verification of installed state, and summaries that
show the compiler error instead of only initial download/compilation chatter.

## Disposition

These are three root-cause groups, not four unrelated Helm failures. At the
initial investigation baseline none was proven fixed since v0.19.1. The later
[diagnostics correction](v0.20-rust-task-diagnostics.md) adds cache preservation,
toolchain/DNS guidance and persisted compiler excerpts with isolated VM evidence;
it does not claim the slint-viewer build is repaired. Some causes are external;
Helm's actionable diagnostics and reproducible execution policy are the product
follow-ups. Keep #562-#564 in the [v0.20 readiness checklist](v0.20-release-readiness.md)
until corrected/verified or explicitly dispositioned by the maintainer. Do not
alter production Rust tools merely to dismiss historical failed tasks.
