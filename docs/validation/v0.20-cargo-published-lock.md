# v0.20 Cargo Published-Lock Upgrade Boundary

Date: 2026-09-27 UTC. Follow-up to #564, stacked on the
[native receipt preservation](v0.20-cargo-receipt-preservation.md) work.
Status: **upgrade implementation and bounded automated/CLI evidence; not issue
closeout or release certification**.

## Policy

Cargo upgrades now request the exact reviewed/task-start candidate with
`--locked`, while preserving the native receipt's crates.io source, install
root, binaries, features, profile and target. There is no unlocked retry,
cargo-binstall fallback, global configuration edit or dependency pin in Helm's
own Cargo workspace. Existing install/reinstall behavior is not changed by this
slice. A published lockfile can retain older dependency vulnerabilities as well
as avoiding newly introduced breakage; it is reproducibility evidence, not a
claim that every dependency is safe or builds successfully.

Because Cargo install accepted missing/stale-root lockfiles in the original
VM probes, the flag alone is insufficient. The upgrade preflight:

1. Runs the selected Cargo executable's native `info --registry crates-io
   <name>@<exact-version>` operation with the same explicitly bound Cargo home.
   It runs at `/`, rejecting root-level project/config overrides, so it cannot
   accidentally inspect or generate a lockfile in the caller's project.
   For a Rustup proxy, Helm resolves the caller's active toolchain before the
   working-directory change and binds it to both stages. It does not install or
   change toolchains; unsupported/ambiguous selection output blocks the action.
2. Requires one unambiguous supported crates.io cache pair. Known sparse and
   Git-index cache identities are supported; unknown candidate layouts,
   duplicate source caches, linked directories/files, oversized archives or
   missing metadata block execution. Cargo's internal cache layout is not a
   stable API; unsupported future layouts fail closed rather than guessing.
3. Reads only the exact `Cargo.toml` and `Cargo.lock` archive members through
   macOS's system `/usr/bin/tar`, using structured arguments, a 30-second bound
   and a combined private 4 MiB output limit. Nothing is extracted to disk.
   Archives are capped at 64 MiB; cache enumeration is capped at 128 entries.
4. Requires the manifest and a unique source-free root lock entry to match the
   exact package/version, supports lock formats 3/4, and compares both files
   byte-for-byte against the source cache Cargo install will use. Absent,
   malformed, unsupported or stale-root lockfiles require manual handling.
5. Revalidates allowed source configuration, the installed receipt and cached
   published metadata before executing the locked upgrade. After success it
   rechecks published metadata and verifies the native installed receipt/version.

Cargo remains responsible for locked dependency resolution and compilation.
This does not independently implement Cargo's resolver, verify every transitive
source, or provide atomic protection against an external process rewriting
Cargo's cache during execution. It does not claim an archive signature or a
new cryptographic supply-chain verifier. Missing Cargo `info` support fails the
native preflight without starting installation; there is no external subcommand
installation or alternate executable fallback.

`cargo.published_lock_unavailable` and its trusted leading marker preserve
actionable CLI diagnostics and localized GUI guidance across all seven locales.
Cancellation/timeouts remain their original error kinds. Signed GUI display
and integrated reviewed executable/scope binding remain separate gates.

## Evidence

All runtime checks used the disposable macOS 27 arm64 VM, with its existing
Cargo/rustc 1.98.1 toolchain and isolated HOME, TMPDIR, database and install roots.
Only compilation/static checks ran on the host. The production app/database,
Rust installation and global configuration were not modified.

- All 55 compiled Rust test executables passed: 821 core unit tests, 237 CLI
  tests, 108 FFI tests and the integration suites; five existing opt-in tests
  remain ignored. Cargo's end-to-end suite includes nine preflight rejection
  scenarios that assert no upgrade invocation and byte-identical old binaries
  and receipt: missing lock, stale published root, modified manifest, unknown
  cache, ambiguous cache, linked lock, metadata failure, cancellation and source
  configuration change during download.
- Native Helm CLI upgrades isolated `sd` 0.7.6 to 1.0.0 with the published lock,
  retaining `--no-default-features`, development profile, binary set, target and
  crates.io source. The native executable and receipt both verify 1.0.0.
  A separate real Rustup-proxy run with a project toolchain override also passes;
  the integration regression asserts identical selection in metadata and install.
- Native Helm CLI also upgrades `slint-viewer` 1.18.0 to 1.18.1 successfully with
  `--locked`, retaining its default features, release profile and target. Both
  native receipt and executable verify 1.18.1. This is the actual package from
  production tasks 229/326, not only the smaller `sd` fixture. Both native checks
  were repeated with the final CLI artifact; no Slint GUI was launched.
- A post-install cache-drift regression separately requires a process-failure
  result explaining that installation may have changed and needs verification;
  it must not mislabel that state as an untouched preflight rejection.
- 18 Swift localization/overflow tests passed in the VM, including trusted-marker
  routing and canonical/bundled locale parity. Unsigned arm64/macOS 13 test build,
  Rust formatting, workspace/all-target Clippy and SwiftLint passed.
- Final CLI SHA-256: `2b2acdac8bc7178c951f36e0da57bde3053522700fc4f2a90d349a73e4b7ebdb`.
  Raw VM evidence is under `helm-certification/cargo-published-lock-20260927`;
  host logs/build products are in this task's ignored `artifacts/`.
