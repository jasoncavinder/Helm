# v0.20 Cargo Install and Reinstall Policy

Date: 2026-09-28 UTC. Follow-up to #564 and the
[discovery-scope upgrade guard](v0.20-cargo-reviewed-scope.md).
Status: implemented with bounded VM evidence, not release/issue closeout.

## Contract

Ordinary Cargo installation now uses the same explicit crates.io published-lock
policy as upgrades. An omitted version is resolved once through native Cargo
search, then an exact SemVer candidate is retained. Metadata download, package
manifest/lock validation and installation use the selected Cargo executable and
Rustup toolchain outside a project working directory. Source overrides and
unsupported configuration fail closed. Missing/stale/unsupported lock metadata
or cache drift never cause an unlocked retry or a different installer fallback.

Fresh installation uses `--locked --registry crates-io --root <absolute-root>
--profile release`, without `--force`. It snapshots existing native receipts and
binary identities before metadata work, rechecks them before mutation, and
verifies the new exact receipt, default feature policy, release profile and
native binaries after success. Unrelated receipts/binaries must be unchanged.
Binary identity uses native filesystem metadata, not a full content hash or
cross-process exclusion lock. Post-execution drift is reported as possible
mutation requiring verification, not a harmless preflight rejection.

Cargo creates two zero-length receipt files when `cargo install --list` first
observes an empty root. Only that paired empty state is accepted as fresh;
legacy content paired with an empty modern receipt, missing modern metadata for
a legacy store, symlinks, unknown receipt fields and malformed identities still
require review. A requested installation may create its storage/cache directories
during preflight, but Helm does not invent native package receipts or replace
binaries there.

An already-installed crate takes the existing receipt-preserving reinstall
path. Source, root, binaries, features, all/no-default-features, profile and target
are retained, rather than reset to default options. The requested exact version
is verified after native completion. Installation is an explicit task-start
request, not a new durable cross-command approval token. Reviewed upgrade
workflows continue to use their separate discovered-scope binding.

## Evidence

Runtime execution is confined to the disposable macOS 27 arm64 VM, using isolated
database, home, Cargo root and build directories. The host production app and
Rust installation are unchanged.

- A genuine fresh Helm CLI install with no version supplied resolves and installs
  `sd 1.0.0`; its native receipt and executable agree. After native configuration
  to no-default-features and the development profile, Helm reinstalls the same
  version and preserves the entire recorded receipt.
- A detached Helm CLI install of `hyperfine 1.19.0` is cancelled after observing
  the real locked Cargo install process. The task persists as cancelled, no
  hyperfine executable appears, and the existing `sd` executable/receipt hashes
  remain identical. An explicit new install then succeeds and the native binary
  reports `hyperfine 1.19.0`. This is cancellation before replacement, not a claim
  that cancellation always rolls back an installation already handed off.
- Regressions cover missing/stale locks, manifest/cache drift, metadata failure,
  executable and unrelated-binary drift, cancellation and uncertain post-install
  results. Native paired-empty receipts, partial/legacy metadata, unrelated
  receipt preservation and untracked binary collisions have dedicated coverage.
- All 55 compiled Rust workspace executables pass in the VM, including 827 core
  unit tests, 237 CLI tests, 108 FFI tests and 12 process-backed Cargo integration
  tests. Five existing opt-in environment tests remain ignored. Host compilation,
  workspace Clippy with warnings denied and formatting checks pass.
- The initial live fresh-install attempt exposed native zero-length receipts
  absent from the fixtures. The narrow correction and regression landed before
  the final complete suite and successful native rerun; the failure was not
  waived or worked around by preinstalling the package.

## Remaining

The published lockfile improves reproducibility but may retain older dependency
versions; it does not guarantee every upstream package compiles or authenticate
the entire dependency graph. Independent native Cargo writers can race Helm;
there is no rollback guarantee. Git/path/private registries, legacy-only receipt
stores and unknown native metadata remain manual, not silently converted.

Keep #564 open for independent review, integrated-head validation and signed GUI
parity. This does not waive first-run, participant, CLT-free, platform/architecture,
external-Sparkle or broader adapter certification gates. No release metadata or
stable version is changed.
