# Cask Binary-Link Ownership Evidence

## Scope

This #607 follow-up interprets installed `binary` declarations as conservative
denial evidence. It does not activate adoption, initialize Sparkle, install an
update or change the Open App fallback. The production adoption provider is
still absent.

Homebrew's [Binary implementation](https://github.com/Homebrew/brew/blob/86e082cb082ab7914d8ffd29685f9ccbdbbbcdbd/Library/Homebrew/cask/artifact/binary.rb)
can adjust the linked source's executable mode. Its
[Relocated implementation](https://github.com/Homebrew/brew/blob/86e082cb082ab7914d8ffd29685f9ccbdbbbcdbd/Library/Homebrew/cask/artifact/relocated.rb)
uses a source basename when the target is absent/empty, while
[Config](https://github.com/Homebrew/brew/blob/86e082cb082ab7914d8ffd29685f9ccbdbbbcdbd/Library/Homebrew/cask/config.rb)
places binaries under the Homebrew prefix's `bin`. Helm reads declarations only;
it never runs Homebrew or reproduces link/chmod behavior.

- Both literal absolute source and destination paths can deny adoption when
  equal to, above or beneath the target app using existing case/Unicode-aware
  component matching. A link outside the app does not hide a source inside it.
- Relative/default destinations use `/opt/homebrew/bin` or `/usr/local/bin`
  only when the native snapshot came from the corresponding exact standard
  caskroot. Receipt architecture, config, current CPU, PATH and environment do
  not choose that root. An explicit absolute destination needs no default.
- Relative sources remain incomplete: a receipt alone does not establish
  staging/`only_path` context. Tilde, wildcard/expansion, dot-component and
  unsupported-root cases preserve known endpoints and a coverage gap together.
  A malformed declaration fails the observation rather than returning clearance.
- Path/receipt/artifact/aggregate bounds, no-follow metadata reads and exact
  raw-byte drift binding are retained. Endpoint processing is filesystem-free.

## Remaining activation gates

This closes one declarative ownership gap, not complete manager coverage.
Shell completions, other artifact forms, hooks, aliases and installer-script
effects remain unresolved; missing/legacy declarations are not clearance.
The real Docker/Parallels/Setapp receipts contain unsupported siblings, so even
an unrelated app still has blocking coverage gaps under the approved policy.
No known gap is overridden by user acknowledgment. Signed operational adoption,
candidate validation, execution/recovery and GUI/CLI parity remain separate
gates before direct third-party updating can ship.
