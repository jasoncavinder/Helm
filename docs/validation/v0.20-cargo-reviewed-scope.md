# v0.20 Cargo Discovery-Scope Binding

Date: 2026-09-27 UTC. Follow-up to #564, stacked on the
[published-lock upgrade boundary](v0.20-cargo-published-lock.md).
Status: **implemented with bounded VM evidence; not issue or release closeout**.

## Contract

Cargo update discovery records an opaque `cargo-review-v1` digest in the existing
source-specific package identifier. It binds the exact candidate, selected
native crates.io receipt and build options, installed binaries, Cargo home,
install root, selected executable, and (for a Rustup proxy) active toolchain and
resolved toolchain Cargo executable. File identity includes canonical location,
device/inode, length, modification/change times and mode. Directory identity
does not include modification time: adding an unrelated package must not
invalidate every remaining action in the same plan.

This is a local drift guard, not a signature, authorization credential, full
content hash or proof of compiler/dependency authenticity. It does not bind the
entire inherited build environment or claim atomic exclusion of external writers.
Existing published-lock, source/configuration and native receipt checks remain
required independently.

- Shared-core discovery publishes `cargo-review-unavailable` when the installed
  receipt/scope cannot be established. Read-only update visibility stays usable;
  mutation fails closed instead of silently executing an unbound update.
- GUI preview/confirmation, individual updates, failed-task retries, legacy
  bulk updates, and foreground/background CLI plan steps retain the discovered
  candidate and scope. Missing old-cache/retry metadata requires a fresh review.
  Retry metadata comes from the submitted task, not a refreshed candidate.
- Core validates the scope before inventory/no-op handling and again after the
  candidate metadata download, before installation. A selected-executable guard
  at the process boundary rejects a later preference override. Post-execution
  executable/toolchain/root drift reports possible mutation requiring verification,
  never untouched preflight rejection or verified success.
- Only the selected package receipt is bound. An earlier legitimate package
  update may change its own receipt without invalidating unrelated planned work.
- Cargo's transport identifier is not appended to GUI package identity or shown
  as a human package identifier in the inspector. Install/uninstall do not inherit
  an upgrade-only target. Snapshot publication still notices scope changes.

Explicit low-level CLI/FFI upgrades without a discovered binding retain the
existing task-start receipt/lock contract; they are not retroactively described
as reviewed snapshot actions. CLI `updates preview` is informational and
`updates run` snapshots the then-current cached plan. This does not introduce a
durable cross-command confirmation transaction. Captured workflow steps cannot
silently change their candidate or scope during execution.

## Evidence

to source/static checks and unsigned compilation; the production app, database
and Rust installation remain untouched.

- Full compiled Rust workspace suites pass in the VM, including scope rejection
  before mutation for changed binaries, options, executable selection, candidate,
