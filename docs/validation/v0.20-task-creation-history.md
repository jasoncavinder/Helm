# Task Creation History and Recovery

## Scope

A native upgrade-path check using a database created by the published v0.19.1
CLI found that runtime activation correctly cancelled an orphaned detection,
but replaced its original creation timestamp with the restart time. The prior
CLI's stale running record is a historical persistence issue already addressed
by the earlier completion-persistence work; this correction concerns its recovery
history, not a claim that current CLI completion is still broken.

`TaskStore.update_task` and `update_task_with_log` now preserve stored creation
time. Transition timestamps remain in logs. The in-memory test store follows
the same contract. No migration version, name or SQL definition changes.

Preserving creation time must not immediately age out recently completed or
recovered work. Retention for completed/cancelled records now uses the latest
matching terminal-state log, with a creation-time floor and a creation fallback
for legacy logless records. Failed tasks retain their existing policy. A later
status-less diagnostic does not extend retention. Expired IDs are selected
before deleting logs, and log/record deletion is one transaction.

## Verification

All runtime verification uses isolated databases in the disposable macOS VM.
The new creation/retention tests and both strengthened FFI recovery tests first
failed against the uncorrected implementation. The native v0.19.1 replay also
reproduced the creation-time overwrite, separately from permitted recovery log
and status changes.

- Full native Rust workspace: 809 core unit tests, 237 CLI unit tests, 108 FFI
  unit tests and all integration suites passed (five existing ignored tests).
  The SQLite store suite now has 51 passing tests, including three new history,
  retention and transactional-rollback cases. Both strengthened FFI restart
  recovery regressions pass.
- Complete migration compatibility gate and workspace/all-targets clippy passed
  in the VM. Formatting, diff and documentation checks passed on source.
- The same unmodified schema-20 backup made by the published v0.19.1 arm64 CLI
  fails the timestamp assertion with the prior integrated library and passes
  with this branch's native library. Each run starts from a new copy; evidence
  and the original backup are preserved. Five separate-process stages cover
  unacknowledged preparation, reopen, explicit acknowledgment, acknowledgment
  persistence and idempotent runtime activation. Original preferences, consent,
  onboarding and prior rows/logs survive; only permitted recovery status/log
  changes and additive migration/experience state are accepted.

  VM evidence is retained under

## Limits

- Existing timestamps already overwritten by older versions are not reconstructed.
- This is not a migration, first-run shipping activation or release approval.
- Native FFI checks do not replace signed GUI upgrade QA.
- The owner's production installation and database are not modified.
