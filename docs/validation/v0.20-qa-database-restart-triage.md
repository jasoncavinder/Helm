# v0.20 QA Database Restart Investigation

Checkpoint: 2026-09-26 HST (2026-09-27 UTC).
Tracking: [#560](https://github.com/jasoncavinder/Helm/issues/560).
Campaign changes remain unmerged in #557/#558 for owner batch review.

## Disposition

The corruption symptom is reproducible under a forced stop of the disposable
macOS VM with Helm's prior WAL/NORMAL connection policy. A narrow candidate adds
`PRAGMA fullfsync = ON` to each shared-core store connection. The candidate passes
the isolated forced-stop scenario with baseline data retained and subsequent
writes accepted. WAL and `synchronous=NORMAL` remain unchanged; this is not a
switch to syncing every commit, a schema migration, or automatic corruption repair.

This supports the macOS flush correction for review, not a claim that every
storage environment is certified or that the original host-restart incident's
precise cause is proved. Keep #560 open through independent review and integration
of the candidate. Do not publish v0.20 or mark the campaign recovery gate closed
solely because the isolated QA cache was rebuilt or these bounded tests pass.

## Approved VM Interruption Experiments

The owner approved one forced stop, then up to three comparisons. Exactly four
forced stops were performed. The idle QA app/service were closed, campaign
evidence was copied off the guest first, and every writer used a new isolated
database. No packages, existing QA database, account state, or manager settings
were changed by the probes. The VM was restarted after each test and left running
with the QA app closed.

Environment: arm64 macOS 27.0 beta, build `26A5378j`; Parallels 27.0.1 (58670),
Apple Virtualization backend, guest-local APFS data volume with ample free space.
This is not Ventura/Tahoe, Intel, or a physical-Mac power-loss certification.

Each probe used Helm's compiled `SqliteStore` to persist doctor scans across all
29 manager scopes, package snapshots, pins and task records. An older reader kept
WAL frames live; every 20 cycles it released its transaction and requested a
truncate checkpoint. The probe made no adapter calls. Runs were bounded to ten
minutes and 50,000 cycles, and were interrupted while actively writing. The
explicit checkpoint reader used the corresponding comparison policy.
In the initial reproduction, that reader instead retained SQLite's default FULL
synchronous setting with fullfsync off; production store writers used NORMAL.

Before any post-restart database connection, each database/WAL/SHM set was
inventoried, hashed, copied and archived to the host. Verification used those
sets, not a database-only copy. The original experiment's preserved WAL has 118
checksum-valid frames and 30 commit markers; it describes 625 pages, while the
main file contains 619 pages and a header declaring 3095. Independent host SQLite
also finds out-of-range B-tree references with the WAL present. This is mixed
persistent state, not merely an absent WAL or an expected rollback of recent work.

| Experiment | Policy | Result |
| --- | --- | --- |
| Initial, isolated writer | WAL/NORMAL, ordinary flush | Malformed database; main header/file 3095/619 pages |
| Comparison 1, three concurrent isolated databases | Existing policy; NORMAL + fullfsync; FULL + fullfsync | All three recover integrity, baseline data and further writes |
| Comparison 2, isolated control | WAL/NORMAL, ordinary flush | Malformed database again; main header/file 3682/3498 pages |
| Comparison 3, isolated candidate | WAL/NORMAL + fullfsync | Pass; main header/file both 4003 pages |

The concurrent comparison is exploratory: one process's stronger device flush
can influence another database. It is not independent baseline-versus-candidate
evidence. The later isolated runs address that limitation. The passing candidate
retained 3420 scans, 99,180 scope rows, 3421 task records, baseline package/pin/task
state, and accepted task reservation 3421 plus scan generation 3421. Integrity and
foreign-key checks passed before writes; integrity passed again afterward.

The first comparison verifier incorrectly expected the seeded reserved task to be
completed. `reserve_task` correctly persists it as queued. The verifier was
corrected, and fresh copies of the same pre-open evidence were checked again.
No writer, preserved database, or interruption was changed/repeated for that
correction. The earlier assertion failures remain in the raw record and are not
classified as product failures.

## Contract and Remaining Limits

SQLite documents that WAL/NORMAL retains consistency but can lose recent commits
after system/power interruption. Its macOS `fullfsync` option requests
`F_FULLFSYNC` at synchronization boundaries; with NORMAL it does not add a sync
after every commit. See [synchronous](https://sqlite.org/pragma.html#pragma_synchronous)
and [fullfsync](https://sqlite.org/pragma.html#pragma_fullfsync).

The observed corruption is not acceptable NORMAL-mode durability loss. Enabling
the stronger flush is supported by the isolated reproduction/candidate contrast,
but that does not uniquely identify a Parallels, beta-OS, filesystem, or SQLite
defect. No claim is made that all acknowledged commits now survive power loss.
The ordinary process tests protect package/pin/task consistency; the connection
policy test ensures each reopened store requests WAL/NORMAL/fullfsync. These
tests and CLI evidence-preservation coverage run in the SQLite compatibility gate.
