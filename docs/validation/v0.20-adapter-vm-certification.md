## Findings

### Follow-up: verified last-tool removal

The #556 correction retains executable identity and records the tool store's
parent and grandparent identity before a reviewed sole-tool uninstall. Only exit
zero plus verified absence of the store and all target entrypoints may produce
an empty post-mutation inventory. A surviving parent must retain its identity;
uv's documented empty-parent cleanup is allowed only while the grandparent stays
unchanged. Replaced paths, dangling symlinks, permission errors and changed
executables are not absence. Missing aliased scopes remain conservative failures.
Read-only refresh does not reinterpret an unrelated missing store as empty or
create directories. Explicit installation can recreate its validated owned store.

The following evidence supersedes the original #556 failure below, not the other
pending matrix cells. Guest runs `uv-real-ks57kgi2` (0.12.18) and
`uv-real-6o9wfudy` (0.12.9) pass the 35-command CLI scenario, including removal of the
last tool, empty cached inventory, expected read-only missing-store rejection,
explicit reinstall, refresh and second last-tool removal. Python remains 3.14.7.
CLI SHA-256 is `91eafc441e36846b28813ea0728e85ab9ae011ac1aeae861111d212bea86f3fe`,
built locally before commit from #557 source plus the uv removal correction.
This is not signed GUI or full adapter certification. Deterministic removal-guard
regressions and the full Rust quality gate also pass. The opt-in core lifecycle
test now includes final-tool removal so this cannot remain an untested edge case.

The owner authorized all manager certifications/fixes and queued PR creation,
but explicitly postponed review/merge until the campaign is complete. Homebrew
7.0.6 was bootstrapped into the disposable guest using its official installer;
formula detect/refresh/search, hello install, native pin/unpin, uninstall preview
and uninstall passed through Helm in `campaign/evidence/brew-20260924-224803.json`.
The manager-family campaign uses an isolated shared HOME and database under
`~/helm-certification/campaign` and installs managers in the guest; this does not
touch the owner's Mac or the guest stable Helm database.

**CLI completion race, corrected in this change.** On the original binary,
`managers detect uv` returned installed=true, but the next `managers show uv`
reported detected=false. Repeated successful refreshes left no cached update,
the final task persisted as running, and a reviewed upgrade was rejected because
no candidate existed. CLI terminal waiting did not drain ordered response
persistence before process exit. Both synchronous paths now await the existing
receipt. Two gated-store regressions failed before the correction and pass after
it. The full Rust quality gate passed, including workspace tests, formatting and
Clippy. No database schema or GUI behavior was changed.

**uv final-tool uninstall, original finding [#556](https://github.com/jasoncavinder/Helm/issues/556), corrected above.**
After the successful lifecycle steps below, removing the final tool removed both
its entrypoint and the store directory. Helm reported `uv scope path cannot be
resolved` instead of reconciling the successful removal. The post-command scope
binding assumes that the store survives. Upstream uv's
[uninstall implementation](https://github.com/astral-sh/uv/blob/0.12.18/crates/uv/src/commands/tool/uninstall.rs)
explicitly cleans empty stores and may also remove their empty parent. This needs
a separately reviewed, narrowly scoped postcondition correction. Do not bypass
binding checks globally or reinterpret arbitrary missing stores as empty.
