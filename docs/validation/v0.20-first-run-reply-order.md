# First-Run Reply Ordering

## Correction

The Debug-gated real first-run entry used `withTimeout` for XPC calls. Timeout
fallbacks are delivered on the main queue, but successful replies retain their
transport callback queue. The new JSON and Boolean wrappers read `connection`
and `connectionGeneration` before entering the controller's main-queue delivery.
Those values are changed by main-queue connection/disconnection handling, so the
pre-delivery reads could race a disconnect or replacement connection.

Both wrappers now use one shared delivery boundary. It asynchronously enters the
main queue before checking connection identity and invoking the controller reply.
The controller's existing generation check still independently rejects replies
superseded between that delivery and its own queued state transition. No callback
publishes synchronously inside a view update.

This does not alter startup consent, repair policy, timeout durations, service
APIs, or shipping activation. It remains stacked on the real first-run work;
signed acceptance and release-route activation are still separate gates.

## Regression Evidence

Three new tests use the same delivery helper called by both production wrappers:

- A background transport reply validates and delivers on the main thread.
- A transport reply is queued while the main thread is held; connection
  invalidation wins before delivery, and no stale reply reaches the controller,
  grants acknowledgment, or activates runtime work.
- A current background reply advances the actual first-run controller to the
  legal gate asynchronously, without granting acknowledgment.

## Reference

[Apple's XPC interruption documentation](https://developer.apple.com/documentation/foundation/nsxpcconnection/interruptionhandler)
describes the connection's reply/handler queue. UI-owned state must be serialized
with the app's main-queue connection lifecycle rather than assuming that transport
callbacks already run on the main thread.
