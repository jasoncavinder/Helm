# External Sparkle Private Ledger

Continuation of #607 after merged #624 (`41024989`). This prepares private
helper storage, not operational adoption or updating. #606/#607/#608 remain open.

## Contract

- The explicit helper command `--prepare-ledger` requires fresh notarized helper
  self-observation and the existing own-framework checks. It uses the OS account's
  `~/Library/Application Support/com.jasoncavinder.Helm.SparkleExternalUpdater/ledger.sqlite`.
  HOME, CFFIXED_USER_HOME, HELM_DB_PATH, preferences and XPC cannot redirect it.
  The bootstrap and app-preflight commands remain database-free. No normal
  app/development database is imported, reset or used as an authority source.
- Native directory opens reject aliases in any path component, unsafe ancestor
  ownership/mutation permissions and unsafe ACLs. The helper namespace must be
  current-account-owned `0700`; files must be regular, singly linked,
  current-account-owned `0600`, with no allow ACL entries. Existing permissions
  are never silently repaired. Parent directories retain their legitimate
  non-mutating read/traverse permissions.
- Bound directory inspection to 32 recognized entries and each file to 256 MiB.
  Check the DB, lock, WAL/SHM/journal sidecars and strictly named migration backups
  before entering core. Symlinks, hardlinks, special files and unknown entries
  fail closed. Retain descriptors through the complete synchronous operation,
  including final flush/revalidation. Revalidate path/object identity, ownership,
  mode and ACLs before acknowledging success.
- A nonblocking exclusive lock serializes cooperating helper preparations.
  Lock/DB creation uses exclusive creation only in a newly created namespace.
  Missing lock/DB files in an existing namespace, partial prior initialization,
  corruption or migration/epoch/session-table failures are recovery work, not a
  reason to recreate storage or issue a new consent epoch. Failed initial setup
  may leave a partial private directory; no destructive automatic cleanup occurs.
- The private C ABI accepts a native-leased path, not serialized trust evidence.
  Core opens the existing file without SQLite CREATE and with NOFOLLOW, validates
  it before normal WAL configuration, then applies the immutable migration
  contract. This namespace starts at schema 24; an older/empty existing store is
  not accepted as new. Existing app-store construction/connection behavior and
  every historical migration remain unchanged. Preparation creates no adoption
  record or update session, and a success result grants no update permission.
- The directory lock is cooperative, not exclusion of every external process.
  This is not tamper-proof storage against the same account/root, hardware-failure
  certification or protection against restoring an old backup. Future native
  session work must retain these checks around every ledger operation instead of
  caching an approved path or returning a bare store beyond the lease.

SQLite documents [NOFOLLOW and existing-file open modes](https://www.sqlite.org/c3ref/open.html).
The native guard is still necessary for directory ownership, aliases, sidecars,
ACLs, bounds and cooperative concurrency; SQLite flags are not a full filesystem
authorization policy.
