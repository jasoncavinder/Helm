# v0.20 Wayfinder Popover Research Readiness

Date: 2026-08-16

Status: owner state, accessibility, localization, placement, and timing matrices complete; whole-workflow and moderated checkpoints remain open

## Scope

This checkpoint closes the implementation-to-research handoff for Native Mac Experience Slice 20.1. It records the production unified Wayfinder popover, the owner-accepted route correction through PR #490, and a deterministic debug-only state seam in the shipping view.

It does not claim a participant session, a whole-workflow synthetic dataset, a whole-workflow accessibility pass, a broader multi-display hardware matrix, or v0.20 workflow sign-off. The bounded popover accessibility and currently available two-display placement matrices recorded below are complete.

## Production Fixture Contract

Debug builds accept `HELM_WAYFINDER_POPOVER_FIXTURE` with one of these values:

| Fixture | Condition | Affected route | Key evidence |
|---|---|---|---|
| `healthy` | Healthy | All current | 17 detected sources; no primary action |
| `updates-ready` | Updates Ready | Apps and Packages | Four reviewed-plan updates |
| `running` | Active work | Apps | Determinate 5-of-12 progress |
| `needs-review` | Actionable finding | Tools / `mise` | Multiple-install decision context |
| `error` | Failed work | Apps | Recovery action and error route tone |
| `offline` | Offline/cached | All cached | Saved-state action; refresh unavailable |

The fixture is projected through `WayfinderProjectionProjector` and `WayfinderPopoverPresentationProjector`, then rendered by the production `WayfinderPopoverView`. It does not use the separate design-lab renderer.

While a fixture is active in a Debug build:

- the popover bypasses onboarding so the requested state is immediately reviewable;
- launch, manual, and reconnect-triggered Helm refresh requests are ignored;
- scheduled, information-only, and manual Helm self-update checks are ignored;
- refresh and Helm-update controls retain their production appearance, but requests safely no-op;
- Release builds ignore the environment key.

The fixture replaces popover presentation only. Dashboard destinations continue to read the development profile, and synthetic task IDs do not create matching Plan or Activity records. Route controls can validate destination/domain wiring, but a full moderated session must not use them as evidence for destination content or workflow completion until the versioned whole-workflow dataset is available.

## Safe Launch

Use a Debug app built from this branch. Debug service builds use Helm's `Helm-Development` database namespace; do not launch this fixture against the stable application bundle or stable user database.

In Xcode, add the fixture key and one state value to the Helm scheme's Run environment. From a terminal, launch the executable directly so it inherits the environment:

```bash
HELM_WAYFINDER_POPOVER_FIXTURE=needs-review /path/to/Helm.app/Contents/MacOS/Helm
```

Quit other Helm development processes before changing fixture states. Use the same build and dataset version for every compared capture.

Debug builds also accept `HELM_WAYFINDER_POPOVER_BENCHMARK_ITERATIONS` from `1` through `100` when a popover fixture is active. The benchmark opens the production panel, records acknowledgement after `makeKeyAndOrderFront` plus app activation, forces the hosted content's layout/display, records first useful render, emits one machine-readable result line, and terminates. Release builds ignore this key.

```bash
HELM_WAYFINDER_POPOVER_FIXTURE=needs-review \
HELM_WAYFINDER_POPOVER_BENCHMARK_ITERATIONS=31 \
/path/to/Helm.app/Contents/MacOS/Helm
```

For a warm series, discard the first sample and retain the next 30. For a cold process series, launch 30 separate processes with one iteration each. Do not purge system caches; report the run as cold process/no application cache rather than cold operating-system file cache.

## Evidence Already Collected

- The owner approved the fixed 400-by-458 composition and requested only bounded visual refinements.
- Production implementation replaced the legacy mini-Dashboard while retaining shared Course truth, stable deep-link metadata, one context row, and Dashboard-owned depth.
- Owner QA found that all route stages initially opened an unfiltered Environment view. The corrected build then passed owner visual verification for System, Tools, Apps, and Packages routing before PR #490 merged.
- Automated projection and route tests cover priority, route tone, finding context, deep-link domain/entity preservation, offline refresh availability, and fixed footprint.
- The owner rendered Healthy, Updates Ready, Running, Needs Review, Error, and Offline through the production-view fixture seam in effective Light appearance (Auto resolving to Light) and explicit Dark appearance using the same arm64 Debug build. All twelve state/appearance combinations passed visual checks for hierarchy, legibility, semantic distinction, fixed footprint, clipping, transparency, and layout stability.
- The initial Needs Review/Light pass exposed a literal percent sign before the localized manager name. The locale catalogs used unsupported `%{manager}` placeholder syntax; both locale trees now use `{manager}`, locale parity passes, and regression coverage checks both affected Wayfinder context keys across every supported locale. The corrected Needs Review fixture passed in both appearances.
- The initial Full Keyboard Access pass skipped all four route controls because each native `Button` was replaced by a custom accessibility element. The route controls now retain their native button accessibility identity while preserving explicit labels, semantic values, and hints. Owner re-test passed one complete Tab and Shift-Tab loop containing the route controls and all previously reachable actions, keyboard route activation, Escape dismissal with focus return, and single outside-click dismissal without flicker or reopening.
- The corrected Needs Review fixture passed the owner VoiceOver pass: logical single-pass order, nonduplicated header/course semantics, named primary and utility actions, individual System/Tools/Apps/Packages button roles, route status values and hints, coherent `mise` decision context, and `VO-Space` routing to the Tools-filtered Environment destination with `mise` selected.
- With Increased Contrast, Reduce Transparency, Differentiate Without Color, and Reduce Motion enabled together, owner QA passed Running, Needs Review, Error, and Updates Ready. Progress remained meaningful without animation, surfaces stayed opaque and legible, and state words, icons, ring segmentation/dashes, and actions distinguished activity, review, failure, and routine updates without depending on color. All four system settings were then verified restored to their original off state.
- German, Hungarian, and Japanese Needs Review fixtures passed at the fixed footprint without clipping, overlap, raw keys, or unreachable actions. Hungarian QA exposed three English utility-menu fallbacks, while the catalog audit found one additional German fallback; both locale trees now localize the complete menu, and regression coverage rejects English-equivalent utility labels in every non-English locale. A copied Debug app with every English value expanded by approximately 40% also passed the fixed-footprint content and utility-menu checks.
- The Needs Review fixture passed owner placement checks at the menu-bar screen edge, on each currently available display, and in an external app's full-screen Space. It remained fully onscreen and correctly anchored, did not substitute the Dashboard, and dismissed cleanly through both outside click and Escape without flicker or reopening.
- Opening-time measurements used the production Needs Review panel in a `113 MB` arm64 Debug app on a MacBook Pro (`Mac17,6`, Apple M5 Max, 18 CPU cores, 64 GB memory), macOS `26.6.1` (`25G76`), on AC power. Available displays were the built-in `1728x1117`-point Retina display at `2x` and a `1920x1080` AirPlay display at `1x`. The projection-only fixture represented 17 detected managers and one `mise` finding; it did not read a synthetic database or submit network/update work.
- Thirty warm cached reopenings passed the `50 ms` acknowledgement and `150 ms` first-useful-render p95 budgets: acknowledgement median/p95/worst was `3.897/11.785/15.070 ms`; first useful render was `4.883/12.592/16.611 ms`. Thirty separate cold-process first openings, without purging operating-system file caches, passed the `100 ms` acknowledgement and `300 ms` shell budgets: acknowledgement was `10.145/22.120/22.995 ms`; first useful render was `14.481/25.462/25.869 ms`. p95 uses nearest-rank selection, and the reported worst value preserves the outlier evidence.

This evidence is implementation and owner-QA evidence, not participant evidence.
