# External Sparkle Data-Free Bootstrap

Status: nonshipping transport foundation, 2026-09-28. Builds on the
[native peer requirements](v0.20-sparkle-peer-authentication.md); it does not
implement or enable direct updating.

## Contract

The standalone `service/external-updater` package now has a bounded client and
per-connection server bootstrap. No helper target, running listener, installation
API, app embedding, entitlement change or signing configuration is added.

The only protocol method is `hello(version:challenge:reply:)`. It carries a
schema version and 32-byte random nonces, never an app path, bundle metadata,
update URL, command, authorization decision or durable operation identity. The
nonce is not authentication: native fixed code-signing requirements authenticate
messages. The client checks the OS-reported peer account after the accepted reply,
not an account asserted in the reply. Both sides reject malformed or repeated
handshakes; the client validates the exact echoed challenge and response shape.

Production construction always uses the fixed peer requirements. The server
accepts a newly received inactive connection and installs its requirement exactly
once before exporting/activating. A future listener must still use the listener
gate. The client configures the helper requirement before activation and does not
send sensitive data to an endpoint simply because it can construct a connection.
Debug-only internal constructors permit unrestricted **test** transports; they
are excluded from Release builds and are not public production API.

A serialized state queue handles replies, errors, deadlines and cancellation.
Ordered consumer events use a separate queue so a blocked observer cannot delay
native invalidation or internal deadlines.
The client starts its monotonic five-second deadline at `begin`; the server's
deadline starts when its accepted connection is configured. A late reply cannot
reopen a closed client. Duplicate begin is idempotent; cancellation before begin
does not contact the endpoint. Connection interruption or invalidation closes the
bootstrap without automatic reconnection. At most one ready event and one closed
event occur. The live connection has a separate 120-second maximum lifetime;
there is no automatic extension or retry. Nonces are not persisted authority.

`ready` means this bootstrap completed, **not** that any app is eligible or an
installation is authorized. The package intentionally exposes no subsequent
operational request method. Future integration must bind its per-connection
context to fresh native target/authority/candidate observations and the reviewed
durable Rust session before any mutation. Connection loss after an actual
installer handoff must retain the durable unverified/reservation semantics, not
infer cancellation from this transport's closed event.

## Evidence

- Host unsigned Debug test compilation and Release package compilation pass.
- All 34 package tests pass in the disposable macOS 27 arm64 VM, including eleven
  bootstrap tests and the prior 23 native observation/peer tests.
  The complete 34-test package passed ten consecutive VM runs.
- The same 34 tests pass with Thread Sanitizer instrumentation in the VM, with
  halt-on-error enabled and no sanitizer report. This is bounded concurrency
  evidence, not proof of race freedom. The unsigned instrumented test bundle
  was compiled on the host, then executed only in the guest.
- Native unrestricted test transport completes the real NSXPC reply/account
  exchange. Production client requirements reject that unsigned helper instead
  of reporting ready; production server requirements separately reject the
  unsigned caller before accepting hello.
- Tests cover malformed version/nonce/session data, a different or root account,
  backwards/deadline time, duplicate hello, cancellation before contact, server
  loss, missing reply and a late reply after the actual five-second deadline.
  A blocked-consumer regression verifies native cancellation independently from
  event delivery, without waiting for the blocked observer to return.
- Strict SwiftLint passes. No host runtime test, app launch, signing or secret
  access was used. VM evidence is retained in
  `/Users/agent/helm-certification/sparkle-handshake-20260928`; local logs are in
  this task worktree's `artifacts/` directory.

The sanitizer run is retained as `artifacts/vm-tsan.log` (SHA-256

## API References

- [Apple: setCodeSigningRequirement](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:))
  requires configuration before activation; malformed requirements are fatal and
  unmatched messages invalidate the connection.
- [Apple: effectiveUserIdentifier](https://developer.apple.com/documentation/foundation/nsxpcconnection/effectiveuseridentifier)
  supplies peer-account evidence. It is not a substitute for code identity.
