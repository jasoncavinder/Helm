# Existing-Only Sparkle Adoption Ledger

Date: 2026-10-04. Base: `5631d665` (#629, including merged #630).
Scope: core prerequisite for #607's authenticated adoption; #606/#608 stay open.

## Contract

`ReviewedLedgerAdoption` provides an existing-only alternative to the general
migrating `SqliteStore` adoption API. The authenticated native coordinator must
own the fixed private ledger path, hold the native filesystem lease, collect
fresh target/helper/boundary facts and admit confirmation on a live session.
This core type does not authenticate a peer, establish sandbox inheritance,
resolve incomplete manager evidence or introduce any helper wire method.

Preparation accepts validated local intent and observations, opens only existing
READ_ONLY/NOFOLLOW storage, validates its exact current schema/manifest/integrity,
and captures the epoch/path revision in one read snapshot. It grants nothing.
The nonserializable review binds the exact database path, target identity/build/
configuration, authenticated-boundary facts, consent ID and prior ledger cursor.

Confirmation consumes that review. Fresh target and boundary observations must
still match all policy checks and the fingerprint; the database path must match.
Clock regression or elapsed time **at or beyond 120 seconds** rejects it. The
same exclusive deadline now applies to the original core adoption API, matching
reviewed revocation. A native coordinator must additionally enforce its own
request/session deadlines independently of callback delivery.

Confirmation opens READ_WRITE/NOFOLLOW without CREATE, waits at most 100 ms for
SQLite lock contention, requests FULL/fullfsync durability and begins an immediate
transaction. It validates the current ledger, rechecks epoch/path revision, safe
mode, consumed consent IDs and active path/device/inode reservations, then appends
the adoption and commits. Both core adoption paths share these atomic checks.
Concurrent confirmations cannot both consume the same reviewed revision.
Revocation committed in WAL fences a pending review. A revoked consent ID stays
consumed; a new grant requires a new explicit review and consent ID.

Missing, empty, corrupt, older, tampered or incomplete storage fails closed:
no recreation, migration, journal-mode switch or missing-epoch repair. SQL writes
roll back on failure. Read-only preparation may still use SQLite's normal WAL/SHM
bookkeeping. FULL/fullfsync requests durability, not a power-loss guarantee.
The native filesystem lease remains necessary around every operation; core's
path/cursor binding is not a substitute for that lease or protection against
same-account/root tampering and historical backup restoration.

An error during storage or a lost reply is not proof of no commit and must not
trigger automatic replay. Later human decisions require fresh history/review.
An adoption receipt grants per-app permission only, never update consent,
session creation, target-reservation release or permission to start an installer.

## Validation

Runtime scope is synthetic temporary ledgers under an isolated HOME/TMPDIR and
database marker; no grants are written to the actual helper ledger. Host work
is unsigned compilation and static checks only. Evidence directory:
`/Users/agent/helm-certification/sparkle-ledger-adoption-20261004`.

On the disposable arm64 macOS 27.0 VM (build `26A5378j`):

- All 916 core unit tests pass, including 12 new existing-only adoption tests.
  Coverage includes read-only preparation, identity/boundary drift, exclusive
  expiry, database-path/epoch binding, safe mode, path/inode reservations,
  missing/corrupt/incomplete/symlinked stores, WAL revocation, consumed IDs,
  concurrent confirmations, bounded lock contention and rollback.
- All 20 private bridge tests pass against the changed core.
- The checked-in SQLite compatibility gate passes: 21 migration contracts,
  three process-recovery checks, one connection-durability check, two real CLI
  recovery checks and two isolated FFI initialization checks. No migration
  definitions changed. Because the VM has no Cargo toolchain, a strict dispatcher
  maps only the gate's exact commands to current host-compiled test binaries;
  the real assertions, child processes and databases execute in the VM.
- Host `cargo test --no-run` builds the four affected/dependent packages for
  arm64 with deployment target 13.0. All-target Clippy with warnings denied,
  formatting, diff checks and docs-sync pass. No runtime tests ran on the host.

## Remaining Gates

The private native bridge and authenticated connection-local adoption review/
confirmation, complete supported ownership exclusions, sandbox-inheritance proof,
accepted Sparkle candidates, live durable sessions, shared GUI/CLI review UX and
real installation/verification/recovery remain separate work. No signed-helper
grant, GUI QA or vendor update was performed by this slice. Shipping Open App,
entitlements, release metadata and helper packaging are unchanged. These tests
do not certify native Intel hardware or Ventura runtime compatibility.
