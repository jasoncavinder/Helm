## Change

The owner approved explicit per-app acknowledgment about custom/unsupported
management after complete supported checks. Known manager claims, failed required
checks and known coverage gaps remain hard blockers. The
[scope contract](../architecture/EXTERNAL_SPARKLE_OWNERSHIP_SCOPE.md) distinguishes
that decision from the native evidence still required before activation.

Adoption request schema 2 requires scope version 1 and an affirmative acknowledgment.
Missing, mistyped, duplicate, false or different-version input rejects before
native observation or ledger creation. The existing single-use review fingerprint
binds these fields. Swift requires an explicit argument, not an implicit default.

Append-only migration 25 preserves old history with NULL scope fields. Such grants
report advisory `scopeChanged` (private ABI code 26), cannot resolve authority and
cannot authorize cached sessions at claim, installation handoff or verification.
Re-review records fresh consent; revocation remains available. Downgrade appends
revocations and rotates the epoch before dropping scope fields, and is blocked
while an external update reservation is unresolved. No earlier migration changes.

A new failure regression exposed legacy duplicate-column tolerance accepting a
partially executed migration batch. Forward migrations from 25 now use strict SQL
execution inside the existing transaction; earlier migrations retain their
historical behavior. The negative fixture verifies DDL and migration-ledger
rollback together without fabricating acknowledgment or losing legacy history.
