# v0.20 Sparkle Private XPC Launch

## Scope and Status

2026-10-05 continuation of #607 from merged #633/#634 (`82633c57`). This stages
an optional private bundled XPC service and establishes a reproducible VM launch
experiment. It does **not** enable production adoption, downloads or installation,
embed anything in the shipping app, or close #606/#607/#608.

The helper still links its own pinned Sparkle 2.9.5 without initializing
`SPUUpdater`. No caller may supply a service name, sandbox assertion, signature
requirement, trusted observation, feed, ledger path or install command.

## Launch Decision

A helper without sandbox entitlements is not necessarily outside the app's
sandbox: directly spawned children inherit restrictions. Apple's
[private XPC service model](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingXPCServices.html)
instead gives services independent sandbox configuration and system-managed
launch. Apple's [SMAppService guidance](https://developer.apple.com/forums/thread/802443)
also rules out installing an unsandboxed job from a sandboxed application on
modern macOS. The staged production route therefore uses private bundled XPC,
not a spawned child or a shipping copy of the old QA LaunchAgent.

`stage --format xpc` permits exactly `XPC!` and
`XPCService = { ServiceType = Application; }`. Runtime self-observation compares
live and freshly validated on-disk signatures, the sealed bundle format, and
filesystem facts. A service must be under an app's `Contents/XPCServices`;
standalone staging is structural validation only. Added service configuration,
wrong placement/suffix and entitlement grants reject. Existing `.app` packaging
and the explicitly invoked QA Mach-service route remain available.

The fixed private connection retains the notarized Developer ID helper
requirement. The OS no-argument service entry performs normal self/framework
checks, then arms the 120-second deadline before resuming its listener.
`NSXPCListener.service()` does not support listener-level code requirements
(documented in the public Foundation SDK header). Its server constructor applies
the exact caller requirement to each connection **before** exporting/activating
it. The same-account check, data-free authenticated hello, eight-request budget,
single-flight deadlines and cancellation/no-reconnect policy are unchanged.

The production adoption provider remains `nil`. Choosing a private connection or
observing sealed XPC metadata does not set `externalHelperUnsandboxed`, establish
complete manager exclusion, or grant consent. This work does not use private
sandbox APIs or weaken the app's entitlements.
