# v0.20 First-Run Startup Boundary

Status: implemented storage-only preparation and explicit runtime activation for
#561. The shipping UI deliberately retains legacy entry until the real Brief,
legal/consent handling, and safe verified action are integrated. This is not the
production route switch or completion of #561.

## Runtime Contract

- Constructing `HelmService` only selects its database URL. It no longer starts
  Rust, recovers tasks, constructs adapters, or starts the CLI update ticker.
- `helm_prepare_startup` / XPC `prepareStartup` creates/migrates Helm-owned
  storage and returns schema-versioned acknowledgment, legacy onboarding/legal
  state, safe mode, and the requested acknowledgment requirement. Storage errors
  return unavailable, not a fabricated fresh profile.
- The first successful preparation binds one absolute database path and one
  acknowledgment policy for the lifetime of the service. Retry/reconnect cannot
  swap databases or weaken an established requirement.
- Only first-run state, acknowledgment, current legal acceptance, and the bounded
  local observer can use prepared storage. Ordinary adapter/status/refresh/mutation APIs remain without
  a runtime. The service's separate CLI-shim installer also rejects early calls.
- `helm_start_runtime` / XPC `startRuntime` explicitly activates normal operation.
  A required acknowledgment is reread from storage; missing, corrupt, or failed
  saves cannot activate it, including through the legacy `helm_init` entry point.
  Concurrent activation is serialized and successful retries are idempotent.
- CLI callers that initialize directly retain normal behavior. A live runtime
  rejects a different database path instead of silently reusing the first one.

Preparation may initialize/migrate Helm's schema. It is not a read-only SQLite
connection, but it does not repair user preferences, recover task history,
execute managers, perform remote checks, or infer new consent.

## App Integration and Remaining Gate

The app handshake now decodes preparation before requesting activation; polling,
deferred refresh, and Helm updater scheduling are enabled only after activation
succeeds. Disconnection stops polling and prevents new updater checks. Network
availability alone cannot enable checks. Deferred manual requests keep priority
over information checks and are consumed once both conditions are ready.
Generation checks discard stale handshake replies, and failed/timed-out replies
use the existing reconnect path. An already executing update is not cancelled by
loss of service connectivity.

Shipping builds explicitly request **legacy compatibility** (no new experience
acknowledgment required). The later [real entry integration](v0.20-first-run-entry-integration.md)
selects the guarded policy only under Debug `HELM_FIRST_RUN_PRODUCTION_QA=1`.
It adds local evidence presentation and durable legal/acknowledgment readback,
not synthetic research progress/receipts. Legal acceptance is not granted by
preparation or acknowledgment. Reviewed action/verification, full session consent,
and the signed fresh/upgrade/offline/interruption matrix remain subsequent work.
Broader CLI setup parity is v0.21. The results below record this boundary's
original validation; the later integration has its own attributable test record.

## Validation

Runtime validation uses only the disposable arm64 macOS VM under
`/Users/agent/helm-certification/first-run-startup-20260927`, with isolated HOME,
TMPDIR, and database paths. The host only compiles and performs static checks;
its production Helm installation is neither launched nor stopped.

- The C-boundary regression runs six isolated child-process scenarios: fresh,
  legacy-completed upgrade, compatibility mode, already acknowledged, corrupt
  marker/retry, and failed acknowledgment save/retry. Each covers rejected early
  normal APIs, unchanged settings/history, no ticker, fixed path/policy,
  non-bypassable initialization, and concurrent/idempotent activation.
- The full FFI library suite passes: 106 tests, zero failures.
- The core library (803 tests), migration matrix (21), process recovery (3), CLI
  recovery boundary (2), and first-run persistence contract (10) pass in the VM.
- Swift coverage checks strict snapshot decoding, legacy completion versus new
  acknowledgment, schema/policy mismatch, both network/startup arrival orders,
  reconnect suppression, and deferred manual intent.
- The complete Swift test bundle passes in the VM: 376 tests, zero failures.
- App/service/test-bundle compilation targets arm64 and macOS 13. Runtime results
  do not imply Ventura/Intel or signed XPC/GUI acceptance of the new entry flow.
- Rustfmt, Clippy with warnings denied, strict SwiftLint, channel policy,
  immutable migration-manifest, docs-sync and diff checks pass. The migration
  script's runtime checks were executed from host-compiled binaries in the VM;
  no test executable ran on the host.

No migration definition, localization catalog, release metadata, manager
installation, production database, or signing credential changes in this slice.

The supplemental signed XPC probe was prepared but not executed: signing with the
existing Developer ID identity was blocked by the safety reviewer under the
repository credential restriction. Explicit owner approval is needed before
signing that isolated probe. No signing-policy workaround was attempted. This
does not invalidate the compiled app/service, VM FFI, or Swift results above,
but signed XPC smoke acceptance remains pending.
