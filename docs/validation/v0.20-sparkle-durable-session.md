# v0.20 External Sparkle Durable Sessions

## Scope

This is shared-core persistence behind the proposed external updater, not an
installer, new CLI/FFI endpoint, signed helper or enabled automatic capability.
It builds on the reviewed-request policy and migration-22 first-run ledger.
Existing vendor-app handoff and Helm's sandbox/distribution behavior do not change.

## Durable Contract

- Only a consumed, locally confirmed in-memory `UpdateSession` can claim a
  durable session. The original 120-second monotonic review window is rechecked
  at claim. Records cannot be deserialized into authorization or resumed work.
- Migration 23 permanently consumes operation IDs until an explicit permitted
  database reset. An immediate transaction and partial unique indexes serialize
  the canonical target path and original device/inode across store handles and
  processes. Distinct targets can proceed independently.
- Before returning from claim or any transition, the connection requests SQLite
  FULL synchronization and macOS full flush. This is stronger than cache-write
  policy, not proof against every host/storage failure.
- Callback transitions compare operation ID, review fingerprint, prior state and
  revision. Stale/wrong/duplicate callbacks cannot overwrite the current receipt.
- A generic event cannot begin installation. `begin_install` re-observes the
  target, candidate and authenticated boundary, matches the original fingerprint,
  rechecks safe mode, and commits `installing` before returning a non-cloneable
  permit. The future helper must consume that permit once immediately before
  invoking Sparkle, and must never call Sparkle on an error path.
- Commit errors are potentially ambiguous. They invalidate the in-memory session
  and never yield a permit or allow authorization retry. Read back durable state;
  do not restore a previous in-memory state and resubmit.
- A successful installer-finished callback permits fresh native version/signature/
  identity verification, not immediate success. Only the uninterrupted verified
  path releases the target with `version_verified`; that is not a relaunch claim.
- Failure/cancellation before installation releases the target but preserves its
  consumed operation ID. Loss/failure after handoff stays `unverified` and locked.
- Restart recovery can page through bounded pending receipts and quarantine an
  exact revision. This fences old callbacks and conservatively retains even a
  pre-handoff reservation. It never resumes, retries or promotes a receipt to
  success. A fresh matching version alone cannot unlock an uncertain installer.
- Task-history deletion does not erase this ledger. Reset/downgrade fails closed
  while any target reservation exists, including unverified results. The reset
  check and schema removal share a write transaction with respect to claims.

No commands, shell fragments, passwords, archive contents or raw process logs
are stored in these records. Target paths and bundle/version identity stay in
the local database and must be redacted in shared diagnostics.

## Verification

All 30 focused external-update tests passed in the disposable macOS 27 arm64 VM,
including 18 new durability regressions. The complete native-built Rust workspace
passed, including 839 core, 237 CLI and 109 FFI unit tests plus integration suites
(five existing ignored cases). The complete SQLite compatibility script passed
in the VM, and static manifest validation confirms 23 immutable entries with the
shared prefix unchanged. Host Clippy, formatting and docs checks passed.

Evidence is retained in VM scope `sparkle-durable-session-20260928` and the task
worktree's `artifacts/native-vm-final.log`. The initial killed-child test looked
up the parent fixture's operation ID rather than the generated child ID; that
harness assertion was corrected before the full passing rerun.

Coverage includes independent-process and thread
claim races, a killed isolated worker, durable readback, rollback-injected handoff
failure, safe-mode changes, late callback fencing, identity drift, quarantine,
version verification, pagination, migration preservation and guarded reset.
No actual app installer, release mutation, forced VM stop or host runtime is used.

## Still Required

The authenticated native helper must collect actual observations and own the
Sparkle lifecycle. Its callbacks must establish installer completion, not merely
download completion or UI dismissal. Quiescence/terminal-result reconciliation
after helper loss needs a separately reviewed implementation before an uncertain
reservation can be released; this slice intentionally offers no generic unlock.
The helper must also coordinate Reset Local Data UX, private diagnostics, service
receipts and GUI/CLI parity. Do not enable this path while those pieces are absent.

Signed/notarized packaging, OS App Management permission handling, real target
download/install/relaunch checks, cancellation/denial/helper-loss recovery and
Ventura/Intel evidence remain open. Source-level and synthetic process tests are
not substitutes for those release gates.
