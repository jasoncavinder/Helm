# First-Run Startup Discovery

## Scope

Follow-up to [#599](https://github.com/jasoncavinder/Helm/issues/599), based on
`dev` after merged #602. The guarded versioned first-run route activated the
service without discovering managers. Ordinary refresh only consumes existing
detections, so a sparse legacy profile remained empty or partially populated.
The explicit CLI discovery used for earlier ordering QA was not a fix.

This change does not enable the shipping first-run switch, acknowledge on the
user's behalf, grant repair consent, install managers, or change updater design.
The controller retains legal/acknowledgment readback and generation fencing.
Legacy startup keeps its existing entry point.

## Implementation

- Versioned activation calls `startRuntimeWithDiscovery`, carrying the current
  path state. Unknown maps to unavailable. Core applies that state before
  coordinator startup, including the automatic self-check ticker.
- Prepared acknowledgment is still required. Discovery is process-local and
  once-only, including already-acknowledged relaunches. Repeated activation or
  client reconnection to the same service cannot duplicate it; a new service
  process discovers again.
- The startup pipeline schedules real ordered detection rather than synthetic
  presence records or the manual API's coalescing guard. An existing refresh
  cannot turn startup discovery into a successful no-op.
- Refresh follows detection. Request-response orchestration waits for its
  existing persistence-completion handle within the original timeout budget;
  execution success alone is not evidence that downstream database readers can
  see the new snapshot. Low-level task terminal visibility remains unchanged.
- Offline startup performs local discovery/inventory. Network refresh/catalog
  work is deferred; a path change during or after the pass cannot drop the
  deferred refresh. Reconnection does not repeat discovery.
- Shared authority/enablement/selected-executable policies remain in force.
  Disabled managers stay disabled; normal discovery may establish an executable
  selection for a newly detected manager. Safe mode and historical consent are
  not changed. No migration or schema identity changes.
- The experimental external file coordinator is not used by this new GUI
  startup contract. An externally owned coordinator is rejected instead of
  starting a second, uncoordinated discovery runtime.
