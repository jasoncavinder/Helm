# Standalone External Sparkle Helper Package

Status: isolated development foundation for #607, based on merged #618
(`47527960`); tested implementation `6282c897`. No direct-update capability, shipping integration or release
publication is enabled. Open App remains unchanged.

## Scope

- Separate `HelmSparkleExternalUpdater` app with exact Sparkle 2.9.5 dependency,
  resolved revision and SwiftPM binary checksum; never a vendor-embedded updater.
- New-output-only packaging with confined rpaths, Ventura Mach-O checks, fixed
  metadata, framework architecture/completeness and contained-tree validation.
  No credentials, signing, registration, launch or publication in the packager.
- Native notarized self-identity and loaded-framework checks before either
  preflight or bootstrap. No `SPUUpdater` initialization or target request API.
- Fixed per-user, bidirectionally authenticated XPC bootstrap with one accepted
  connection and 120-second process limit. Existing five-second handshake,
  same-account and close-on-loss behavior is retained; no retry or fallback.
- Separate data-free QA test host, never embedded/shipped/launched on the host.
  Main Helm app entitlements and signed accepted owner-QA profiles are unchanged.

The helper's copied Sparkle distribution contains upstream installer components,
but this executable never invokes them. Bundling those components is not an
installation test or an advertised ability to update other apps.

## Verified Evidence

Host compilation/staging/static inspection only; runtime checks in the disposable
macOS 27 arm64 VM, under the new isolated
`/Users/agent/helm-certification/sparkle-helper-package-20261002/` scope.

- All **49 native package tests** pass, with zero failures.
- All **17 packaging regressions** pass. Negative cases cover replacement and
  symlink destinations, set-id/special/escaping input, wrong/missing framework,
  unsupported/missing architecture, wrong minimum OS/dependencies/rpaths, invalid
  build and changed/enabled metadata. Mocked native-tool outputs are not real
  signature or universal-runtime evidence.
- Real arm64 Debug/test and arm64/x86_64 Release builds pass. Staging/verifying a
  real universal helper passes; Intel compilation is not Intel runtime acceptance.
- Developer ID signing and deep/strict signature verification pass for the
  separate helper and sandboxed data-free test host. Credentials are not modified
  or transferred to the VM. Nested Sparkle components are signed inside-out.
- Before Apple submission, the real signed but **unnotarized** helper exited 1
  with `invalidSignature` in the VM. This is preserved pre-submission rejection,
  not a claim that removing a staple makes an already-notarized code hash untrusted.
- An attempted operational command is rejected with usage/exit 64, without
  entering preflight or accepting the target path.
- Strict SwiftLint passes with caching disabled. The first lint attempt reported
  zero violations but failed to write its sandbox-restricted cache; the no-cache
  rerun is the successful result.
- Docs synchronization and the VM Sparkle/appcast checklist pass. The latter
  includes intentionally failing rehearsal stubs as regression cases, not an
  actual release rehearsal, tag, workflow dispatch or publication.

Logs/builds/QA signing scripts remain in the task worktree's ignored `artifacts/`.
CI adds portable packaging regressions plus real unsigned arm64 staging alongside

## Signed Peer Acceptance

On 2026-10-02 the owner configured local Keychain authentication and explicitly
authorized QA-only Apple submission. No credential was printed, exported to the
VM or copied out of CI. The tested implementation and native requirements remain
`6282c897`; this continuation changes evidence/docs, not the helper binaries.

Apple returned Accepted with no issues for all three submissions:

Tickets were stapled/validated on the host and revalidated after transfer to the
VM. Each bundle passes strict/deep signature checks and Gatekeeper assessment as
Notarized Developer ID. The real helper's `--preflight` now succeeds, observing
its exact identity/account/build and its own Sparkle 2.9.5, with direct updates
still false. This is actual positive native evidence, not injected observation.

The temporary per-user service runs only in the VM. Launch Services starts the
test app in the logged-in GUI session. `open -W` exit status means launch/wait
success, **not** the child app's exit status; acceptance assertions use explicit
child output and both endpoints, while negative assertions require the child's
bootstrap rejection and absence of authenticated readiness.

| Case | Result |
|---|---|
| Exact notarized sandboxed caller and helper | Both endpoints report authenticated readiness |
| Notarized same-team caller, wrong bundle ID | Caller reports interruption; no authenticated helper event |
| Exact caller ID/team, wrong signed channel | Caller reports interruption; no authenticated helper event |
| Exact caller ID/team/channel, no sandbox entitlement | Caller reports interruption; no authenticated helper event |
| Notarized same-team impostor helper | It receives the data-free hello; the real client rejects its reply as a transport failure |
| Fresh valid session after the negative cases | Both endpoints report authenticated readiness again |

Each case removes only its own LaunchAgent registration in a `finally` block.
Final `launchctl print` reports the test service absent. No shipping app, package,
manager, database or accepted owner-QA profile is changed. The named lookup
exception is confined to the sandboxed QA wrapper; shipping Helm entitlements
are unchanged. Code requirements, including notarization, were never relaxed.

Harness corrections are preserved separately: sandboxed host `stapler validate`
could not inspect Launch Services metadata, then passed outside that shell
sandbox. An SSH-launched unprivileged `launchctl asuser` could not switch audit
sessions; the test was corrected to use Launch Services, without elevation or
loosening any product gate. Neither attempt is counted as a peer/product failure.
