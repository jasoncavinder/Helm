# Standalone External Sparkle Helper Package

Status: isolated development foundation for #607, based on merged #618
(`47527960`); tested implementation `6282c897`. No direct-update capability, shipping integration or release
publication is enabled. Open App remains unchanged.

## Scope

- Separate `HelmSparkleExternalUpdater` app with exact Sparkle 2.9.5 dependency,
  resolved revision and SwiftPM binary checksum; never a vendor-embedded updater.
- New-output-only packaging with confined rpaths, Ventura Mach-O checks, fixed
  metadata, framework architecture/completeness and contained-tree validation.
  No credentials, signing, registration, launch or publication in the packager.
- Native notarized self-identity and loaded-framework checks before either
  preflight or bootstrap. No `SPUUpdater` initialization or target request API.
- Fixed per-user, bidirectionally authenticated XPC bootstrap with one accepted
  connection and 120-second process limit. Existing five-second handshake,
  same-account and close-on-loss behavior is retained; no retry or fallback.
- Separate data-free QA test host, never embedded/shipped/launched on the host.
  Main Helm app entitlements and signed accepted owner-QA profiles are unchanged.

The helper's copied Sparkle distribution contains upstream installer components,
but this executable never invokes them. Bundling those components is not an
installation test or an advertised ability to update other apps.

- All **49 native package tests** pass, with zero failures.
- All **17 packaging regressions** pass. Negative cases cover replacement and
  symlink destinations, set-id/special/escaping input, wrong/missing framework,
  unsupported/missing architecture, wrong minimum OS/dependencies/rpaths, invalid
  build and changed/enabled metadata. Mocked native-tool outputs are not real

- Real arm64 Debug/test and arm64/x86_64 Release builds pass. Staging/verifying a

- Developer ID signing and deep/strict signature verification pass for the
  separate helper and sandboxed data-free test host. Credentials are not modified
  or transferred to the VM. Nested Sparkle components are signed inside-out.
- The real signed but **unnotarized** helper exits 1 with `invalidSignature` in

  entering preflight or accepting the target path.
- Strict SwiftLint passes with caching disabled. The first lint attempt reported
  zero violations but failed to write its sandbox-restricted cache; the no-cache

- Docs synchronization and the VM Sparkle/appcast checklist pass. The latter

## Remaining Gates

The owner explicitly approved Apple notarization of the QA-only bundles. They
are signed and ready, but no local notarization authentication profile has yet
been identified and **no Apple submission or notarized acceptance is claimed**.
Use the existing approved setup without exporting credentials or repurposing CI
secrets. Once available, submit the QA bundles, retain Apple's acceptance/logs,
staple and revalidate, then transfer the resulting artifacts to the VM. Test real
accepted and rejected peers through a temporary per-user LaunchAgent; require
both endpoint evidence, preserve failed attempts and remove only that test job.

Do not weaken the `notarized` requirement to make the test pass. A sandboxed
identity-matching test-host wrapper belongs only in the disposable VM, not the
host's app installation or stable data namespace. No package update is necessary
for this handshake test.

#606/#607/#608 remain open. Shipping launch/installation strategy, native target
authority/candidate mapping, durable-session binding, helper-path security and
sandbox-inheritance proof, real download/install/relaunch/cancellation/recovery,
and Ventura/Intel runtime evidence remain separate gates. No accepted first-run,
Cargo or uv owner matrix needs repeating for this isolated package change.
