## Contract

`reviewAdoption` and `confirmAdoption` connect bounded XPC intent to the existing
private adoption bridge and existing-only helper ledger. **Production adoption
remains disabled:** normal server construction supplies no adoption provider.
Both methods reject without opening a ledger. Only the Debug test initializer
accepts injected providers; there is no preference, environment switch, probe
command or wire assertion that enables production grants. A successful hello
does not advertise adoption capability.

The request contains only schema version, consent ID, target path, expected
bundle identifier and expected installed build. Core validates strict bounded
intent, allowed roots and Helm self-update exclusions before native observation.
A random 32-byte handle belongs to one pending worker-confined review on one
connection. Replacement, malformed review, any confirmation attempt and connection
closure consume or clear that review. Adoption and revocation share the existing
eight-request limit, 8 KiB bound, 15-second request deadline, 120-second session
deadline and exclusive once-per-request mutation admission.

The native processor requires an explicitly complete ownership snapshot. It
rechecks the full target/boundary/ownership snapshot and native account root
around preparation and confirmation, holds the existing-only filesystem lease
around core calls, and admits the confirmation synchronously on the live
connection gate immediately before entering core. Native collection runs on a
separate worker, so timeout and cancellation handling remain responsive.

Preparation is read-only. Rejection before admission cannot write a grant. After
admission, failed observation or lease postchecks return uncertainty, including
when consent actually committed. Session loss suppresses late success but cannot
promise to undo an admitted write. The client never automatically retries or
confirms. The result codes are 50 (review handle), 51 (consent recorded), 52
(review changed/rejected) and 53 (outcome unknown). None approves an update or
creates an executable update token. A lost result requires fresh history and a
new human decision, not replay.

The processor does not establish the truth of injected boundary flags or complete
ownership. Production enabling still requires fresh native peer, sandbox and
ownership proof. A hello or missing entitlement is not sandbox-inheritance proof;
an empty exclusion list is not complete ownership evidence. Shipping Open App,
entitlements, helper identity requirements, migration definitions, release
metadata and credentials are unchanged.

## Remaining Gates

Implement and validate the fresh native boundary/ownership provider, then run
signed-helper acceptance/rejection before enabling operational adoption. Accepted
Sparkle candidates, durable live update sessions, shared GUI/CLI review and
adoption UX, installation, verification and recovery remain separate gates. This
slice does not certify native Intel hardware or older macOS versions and needs no
new owner-facing GUI QA yet.
