# v0.20 External Sparkle Peer Authentication

Status: inactive native connection foundation. No production listener, updater
protocol, installer or capability is enabled. Builds on the
[read-only observer](v0.20-sparkle-native-observation.md).

## Contract

`ExternalUpdaterPeerAuthentication` uses public macOS 13 Foundation APIs to set a
code-signing requirement before a listener or connection is activated. Identity
constraints are fixed in source, not derived from request fields, paths, process
IDs, preferences or environment variables.

- Incoming peers must be the exact `com.jasoncavinder.Helm` Developer ID app under
  team `V73WPJR9M4`, with the signed `developer_id` distribution field and sandbox
  entitlement. Sibling app identifiers and other distribution profiles fail.
- The client's response peer must be the exact separate
  `com.jasoncavinder.Helm.SparkleExternalUpdater` Developer ID identity/team,
  without the app sandbox entitlement.
- Both requirements include notarization and exclude get-task-allow, disabled
  library validation and DYLD-environment injection entitlements. There is no
  unsigned/development fallback. Requirement compilation failures throw before
  Foundation's exception-throwing setters are reached.
- The listener-level requirement screens peers before its delegate. The future
  delegate must also apply `admit` to each new inactive connection before setting
  an exported object or activating it; that gate checks the incoming OS account
  and configures per-message enforcement. The process itself must be non-root
  and not setuid.
- Interruption permanently invalidates a configured connection instead of using
  NSXPC's automatic reconnection possibility. Durable loss quarantine remains
  the runtime's responsibility.

`admit` returning true means configuration only, not that a message has passed
authentication. The future runtime must not translate it into trusted boundary
Booleans. Native accepted message delivery, fresh self/target observations,
account checks, coordinator authority and durable review remain required.

The outgoing requirement authenticates responses, not proof that an initial
request could never reach an impostor endpoint. Complete a data-free authenticated
handshake, validate the peer account and bind its live session before transmitting
an operation or private target data. No operation protocol is introduced here.

## Evidence

Unsigned host compilation only; runtime testing in the disposable macOS VM:

- The full package passes 23 tests (17 observer and 6 peer tests).
- A real unrestricted anonymous-XPC positive control replies successfully.
- The fixed listener gate rejects the test host before the delegate is called.
- A separate test deliberately omits that listener gate and verifies that the
  incoming connection's requirement prevents delivery to the exported object.
- The client gate rejects an impostor helper reply. Native requirement compilation
  succeeds and Security.framework rejects the test process against both exact
  production identities.
- The six peer tests pass ten consecutive VM runs. Strict SwiftLint passes.

Evidence: `artifacts/peer-auth-vm-tests.log` and
`artifacts/peer-auth-vm-repeated.log`; VM scope `sparkle-peer-auth-20260928`.
No app/helper was signed, notarized, installed, launched or modified; no trust
store or credential was accessed. Anonymous test connections expose only an
isolated `ping` fixture, not an updater API.

This does not certify acceptance of the actual signed/notarized peers, a live
cross-account rejection, shipping sandbox access, Ventura/Intel runtime, helper
packaging or the installer. Those gates remain open and separately attributable.
