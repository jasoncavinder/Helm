Continuation of #607 after reviewed/merged #628 (`9932f2e1`). This expands

## Contract

- Inspect every path in the already validated native bundle tree, not only the
  app root, Info.plist and executable. The scope includes directories and symlinks
  actually enumerated by the existing filesystem observer; it does not synthesize
  or follow additional alias paths. Reject empty, duplicate, foreign, escaping,
  control-character or oversized scope before querying receipts.
- Use the OS `/usr/sbin/pkgutil --volume /` interface, not private receipt files.
  Repeated `--file-info-plist PATH` options produce individual XML documents.
  Each batch requires every exact echoed path in order and rejects missing,
  duplicate, reordered, extra or malformed documents. Keep complete replies for
  drift comparison, including receipt metadata rather than package IDs alone.
- A pass permits at most 4096 inspected paths, 32 per batch, four concurrent
  system children, 64 KiB combined stdout/stderr per file-info child and 4 MiB
  total file-info output. Every worker is joined before returning. Results are
  retained in deterministic batch order; any failure rejects the whole pass.
  The shared monotonic three-second budget covers catalog queries, file queries
  and parsing; each child is limited to the lesser of one second and the remaining
  budget. Existing child cleanup, closed input, fixed environment and structured
  argv remain. Bounds do not guarantee hard real-time OS scheduling.
- Collect at most 1024 unique, bounded receipt IDs using `--pkgs-plist`, then
  exact ID/root-volume metadata using batched `--pkg-info-plist`. IDs must be
  safe concrete command operands, never options or regular expressions. No
  caller-provided catalog, prefix, receipt path or query flags are accepted.
- For non-root install locations overlapping the target, query `--export-plist`.
  Bind its ID, volume, version, install time and location to the catalog metadata.
  Normalize relative payload paths lexically, refusing escapes and controls.
  Use fixed POSIX-locale case folding and canonical Unicode composition only for
  overlap/containment denial keys, retaining path-component boundaries. This
  conservatively excludes case-equivalent claims even on case-sensitive volumes;
  it does not prove filesystem identity, follow aliases or authorize updates.
  Metadata binding and raw response drift comparisons remain exact.
  A receipt claiming the app or a descendant is a conservative exclusion, even
  if that payload is now absent. Catalog limits are 256 KiB for IDs, 64 KiB per
  metadata batch, 2 MiB per relevant export, 100,000 exported paths and 4 MiB
  aggregate output. The catalog shares the pass deadline, not an extra budget.
- This supplement is necessary on the VM: file-info queried at the actual
  installation path returned no claim for a non-root-location receipt, while
  querying its root-relative BOM spelling did. The supported export correctly
  identifies both install location and payload. Do not interpret the first
  response alone as absent ownership. No private BOM parsing is used in product.
- Compare complete catalog/export/file-info replies across signature validation,
  then revalidate the bundle and ancestors. Query errors, limits or drift are
  never partial successful coverage. This is not an atomic receipt/filesystem
  reservation and does not exclude changes after observation.

The VM's Apple `pkgutil(1)` manual documents multiple commands in order,
file-info plists, package metadata and receipt exports, and directs callers away
from private receipt storage. The product observer needs no Command Line Tools;
`pkgbuild`/`installer` are used only to create the disposable certification fixture.

## Remaining Limits

No-marker evidence remains unresolved with `canUpdate: false` and
`requiresAuthorityResolution: true`. Nonstandard Homebrew prefixes, marker-less
Setapp integrations, receipt-less/custom management and root-location receipts
claiming historical or alternate-alias paths absent from the inspected tree are
not complete coverage. Receipt existence is a conservative denial, not proof
of active ownership. Unsupported/large/slow receipts may reject an otherwise
valid app; they must not silently permit adoption. Keep the broader supported
ownership policy and operational grant/session/candidate gates open.
